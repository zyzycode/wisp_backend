# API чата — черновик для обсуждения

Это предложение для согласования с фронтом, не зафиксированный контракт.
Backend выбирает LLM-провайдера, модель и параметры. Фронту эти детали не нужны.
Ошибки и их формат обсудим отдельно.

## Отправка сообщения

`POST /v1/chat/completions`

```json
{
  "messages": [
    {"role": "user", "content": "Привет!"}
  ],
  "stream": false
}
```

Пока предлагаем передавать историю диалога целиком в `messages`.
Роли сообщений: `system`, `user`, `assistant`; содержимое — текст.

Обычный ответ:

```json
{
  "text": "Привет! Чем помочь?",
  "finish_reason": "stop",
  "usage": null
}
```

`finish_reason` — причина завершения, `usage` — расход токенов, если доступен.
Нужны ли эти поля фронту — вопрос для обсуждения.

## Постепенный вывод ответа

При `stream: true` предлагаем SSE в ответе на тот же POST:

```text
event: delta
data: {"type":"delta","text":"Привет!"}

event: done
data: {"type":"done","finish_reason":"stop","usage":null}

```

Фронт дописывает `text` из событий `delta` и завершает вывод по `done`.
Для POST поток читается через `fetch`; стандартный `EventSource` для этого не подходит.

## Что согласовать

- Передаёт ли фронт историю целиком или нужны серверные диалоги с `conversation_id`?
- Нужен ли потоковый ответ сразу?
- Достаточно ли текста или нужны вложения?
- Нужны ли разные режимы ассистента? Сейчас предусмотрено необязательное поле
  `assistant` (по умолчанию `default`) и `GET /v1/assistants` для списка режимов.
- Нужны ли фронту `finish_reason` и `usage`?

Имена полей, адреса и состав ответа можно изменить по итогам обсуждения.
